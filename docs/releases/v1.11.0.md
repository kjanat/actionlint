v1.11.0 makes actionlint easier to run as a GitHub Action and makes ShellCheck findings easier to locate. The release adds a prebuilt action image, structured results, more precise source locations, and a substantial refresh of the build and release checks.

## Run the first-party GitHub Action

You can now use the fork directly in a workflow:

```yaml
on: push
permissions: {contents: read}
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - id: lint
        uses: kjanat/actionlint@v1.11.0
        with:
          format: json
```

The action pulls a prebuilt image containing actionlint, ShellCheck, and pyflakes. It supports GitHub annotations, several output formats, and options for files, configuration, working directory, and failure behavior. Structured outputs include `result`, `exit-code`, `problems-found`, `problem-count`, and the formatted output, so later steps can use the result without parsing console prose.

The action image is published under `action-{version}`, `action-v1`, and `action-latest`; the moving `v1` Git tag is also maintained. Use the exact release tag when you want to select this historical version. As a Docker action, it needs a runner with a working Docker daemon.

Thanks @norwd for kjanat/actionlint#5, following the requests in rhysd/actionlint#257 and rhysd/actionlint#479.

## Get ShellCheck findings on the actual script line

For literal block and plain `run:` scripts, ShellCheck findings now map back to the relevant YAML line and column, including the diagnostic range. For example:

```yaml
on: push
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: |
          echo $GITHUB_REF
```

With ShellCheck installed, its quoting diagnostic points at `$GITHUB_REF` inside the script. That makes editor navigation and GitHub annotations more useful when a `run` block contains many lines. Scalar forms that cannot be mapped safely retain the fallback location at the `run:` key.

This addresses rhysd/actionlint#88 and rhysd/actionlint#360, building on the direction explored in rhysd/actionlint#556. Thanks @dpsutton.

## A Go action entrypoint with earlier input validation

The action entrypoint is now a Go program using the actionlint library directly. Existing inputs, outputs, formats, and failure behavior remain unchanged. The change removes the Python wrapper from the entrypoint; pyflakes remains an optional lint integration and is included in the action image. Related: kjanat/actionlint#16.

Configuration and workflow paths are contained within the workspace. Option-like paths and output destinations that are directories are rejected before linting, and execution has a time limit. The CLI image now uses `/w` as its default working directory, making mounted-workspace use consistent.

## More dependable builds and release preparation

Source builds now require Go 1.26 or newer, with Go 1.27 used by CI. The CI matrix was reorganized around targeted platform jobs plus race and coverage checks, superseded PR runs are cancelled, and action and Docker base-image references are pinned. Related: kjanat/actionlint#14.

A Go version-bump tool replaces the Bash script. It checks every declared version replacement, requires release notes, refuses a dirty checkout or an existing release tag, and only pushes when explicitly asked. Releases are serialized before moving image aliases. These checks help prevent a release from containing a mixture of old and new references. Related: kjanat/actionlint#17.

JavaScript tooling now shares a root npm workspace and lockfile (kjanat/actionlint#15). The command manual is restored on the Pages site at `usage.html` and `man.html`, with a `404.html` fallback. Integration documentation clarifies which tools use this fork or upstream actionlint, and the Playground starts with updated action versions.

Upgrade if you want a ready-made GitHub Action or more precise ShellCheck annotations. See the [usage documentation for this release](https://github.com/kjanat/actionlint/blob/v1.11.0/docs/usage.md).
