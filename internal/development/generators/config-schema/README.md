# Configuration schemas

Run `mise run generate:config-schema` from the repository root to update
`actionlint.schema.json`. The schema describes tool selection, whether each tool
is enabled, and tool settings supplied inline or through a configuration file or directory.
`tools` lists one entry per bundled
provider manifest under `internal/plugins/manifests/bundled`; each manifest's
`config_schema` describes inline `config` settings and its `config_shorthands`
appear beside the host keys with the schema of the property each one sets.
Any other `tools` name may belong to a plugin's provider, so it is described
by the host keys alone. A `config_schema` equal to a snapshot under
`schemas/<name>/` is referenced with a `$ref` relative to the main schema's
location, as the ShellCheck directives reference `schemas/shellcheck/0.11.0.schema.json`;
any other schema is embedded.
The root and tool schemas omit `$id` so their retrieval location determines reference resolution.
An installed npm package uses its bundled schema; a versioned CDN URL or Git
commit URL uses the schema from that same release or revision.

The root schema defines shared levels, group levels, presets, rule settings,
plugin settings and backends under `$defs`. Rule properties reference these
definitions and carry their own descriptions. Rule-specific option schemas use
`allOf` to apply their constraints alongside the shared settings. Tombi validates
these constraints without discarding them when resolving a `$ref`.
`actionlint config schema` uses the same
definitions for installed plugin rules, including rejection of unknown setting keys.

Rule selectors reference `rule-name`. Its `known-rule-name` branch supplies
completion choices from the catalogue; a nonempty string branch accepts plugin
names absent from the published schema. Configuration loading validates those
names against registered rules. `actionlint config schema` adds loaded provider
rule names to the shared completion list without duplicating built-in names.

Each rule declaration owns its current name and aliases. An alias's `deprecated`
flag produces a `const` schema branch with `deprecated: true` and a description
naming its replacement. Rule-setting keys carry the same annotation. The open
string branch does not mark unrelated plugin names as deprecated.

Tombi reads `x-tombi-toml-version` to select TOML 1.1, which the configuration
parser supports. Completion labels identify rule names, tool names, variables,
environments and file patterns. `deprecationMessage` tells Tombi which rule name
replaces a deprecated alias. Root keys follow the schema's order when Tombi formats
the file. Arrays are not sorted because settings such as `extends` depend on
their order. See [Tombi's schema extensions](https://tombi-toml.github.io/tombi/docs/json-schema/).

`internal/input/configuration/rules.Levels()` and `Presets()` supply the accepted value sets
to validation and generation. `Categories()` uses the category list from the
shared rule declarations, so configuration does not introduce another list.

Generation requires `dprint` on `PATH`. The generator formats its output through
`dprint fmt --stdin` using the repository configuration before writing the file.
The formatting test compares generated bytes with the committed schema and checks idempotence.

Runtime configuration parsing does not download schemas. Tests check relative
resolution for local packages, CDN releases and Git revisions with external
loading disabled.

## Ruff definitions

The host schema describes tool selection, enablement, and the shape of the Ruff
wrapper. It leaves rule selectors, target versions, preview behavior, and the
contents of `config` to the selected engine. For native analysis, the Ruff
executable validates the options. WebAssembly engines expose `validate_config` for this.
The engine's metadata carries its configuration schema.

The root schema provides small completion examples without constraining settings
to one bundled Ruff release. Tests exercise base and override settings through
the parser, JSON Schema validator, and the real YAML language service offline.
Run `bun install --frozen-lockfile` first for the language-service test.

`schemas/ruff` archives published Ruff snapshots; configuration decoding and schema
generation use the selected engine's schema instead.

## Updating tool settings

The integration supplies its configuration schema through `config_schema` in its
manifest. When its accepted settings change, update that schema and regenerate
the root schema. This generator reads the supplied schema; it does not derive
tool settings from host Go types.

`TestBundledProviderSchemas` checks that generated tool settings match the supplied
schemas. Previously published snapshots stay available at their existing URLs.
